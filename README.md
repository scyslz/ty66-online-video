# 影音列表

单文件 Go 服务：抓取上游列表、解析视频直链，提供一个按条数分页的浏览页面。

## 快速开始

```bash
./run.sh                 # 默认 :8000
ADDR=:8080 ./run.sh      # 换端口
```

首次启动时库是空的，打开页面会触发第一轮抓取（约 10 秒）。

## 代码结构

| 文件 | 职责 |
|---|---|
| `main.go` | 入口：解析参数、启动流水线、优雅关闭 |
| `store.go` | `store` 的数据结构、常量、构造，以及全局锁约定 |
| `persist.go` | 落盘：载入、原子写入、后台合并保存 |
| `list.go` | **列表流水线**：唯一的列表抓取者，增量合并、排详情队列 |
| `detail.go` | **详情流水线**：worker 取队列，解析播放地址并写回 |
| `paging.go` | **分页读取**：只读缓存 + 缺页时对所有站点并发补下一页 |
| `order.go` | **展示顺序**：每站点一个去重的双向队列（插入头部/追加尾部均为 O(1)） |
| `queue.go` | **补页队列**：固定 worker 池 + 严格去重（同一页在途只抓一次） |
| `accessors.go` | 只读访问器：映射导出、来源统计、过期重排 |
| `http.go` | HTTP 路由与各接口 |
| `proxy.go` | **线路二**：视频同源反向代理（清单重写、白名单、SSRF 防护） |
| `index.html` | 前端页面（单文件，无构建步骤） |
| `*_test.go` | 测试与假上游 |
| `provider/provider.go` | **站点抽象**：`Provider` 接口与站点无关的公共工具 |
| `provider/siteutil/` | 各站点共用的 HTTP 抓取与节流闸 |
| `provider/t66y/` | 论坛型站点实现（列表表格 + 详情跳转 + 播放器接口/嵌入页） |
| `provider/demo/` | 示例站点（JSON 列表 + JSON 详情），接入新站可照抄 |

## 数据流

```
列表线程（每 3 小时，增量）
  └ 从第 1 页往下翻，逐条与本地 id 比对
    撞上已有 id 就停（已追平上次同步位置）；一直撞不到最多翻 5 页
                                        ↓
详情线程（-lazy=false 才会主动跑）
  └ 取 id → 抓帖子页 → 解析播放页 → 解析直链 → 写回映射
                                        ↓
                                    store.json（原子写入）
```

映射以**站点 + 帖子 id**（`站点:id`）为主键，所以列表怎么变都不会丢已解析的地址：

- 新帖置顶：只解析新增的那几条
- 帖子翻到下一页：映射跟着 id 走，不重复解析
- 帖子从列表消失：映射仍保留 30 天（`-keep`），`/api/map` 里标记 `listed:false`
- 服务重启：直接从 `store.json` 恢复，零上游请求
- 多站点：各站页号、帖子号互不冲突（页键是 `站点/页号`）

## 分页与异步补页

读取窗口是**只读缓存 + 异步补页**，请求不会被上游拖住：

```
前端翻到某一页
  ├─ 后端立即用缓存里已有的数据返回（毫秒级）
  │    若缓存条数 < offset+limit：返回 loading=true, has_more=true
  └─ 同时把所有站点「未到最后一页」的下一页请求投给后台，立即返回
       列表线程并发抓取（同站点串行 + 最小间隔，跨站点并发）
       前端看到 loading 就每 700ms 重取一次，最多 12 次
```

补页规则：

- **触发条件**：缓存总条数 < `offset+limit`（本页填不满）
- **抓取范围**：所有站点各取一页，**已经到最后一页的站点跳过**
- **到末尾的判定**：上游返回空列表即视为到底（`empty` 标记），之后不再请求
- **深挖上限**：单站点默认最多挖到第 30 页（`-max-pages`），防止前端一直翻尾
  就把上游全站抓一遍
- **站点熔断**：连续失败 3 次熔断，首次冷却 30 分钟；冷却结束后自动放行
  一次试探请求，成功即恢复、失败则冷却翻倍（上限 6 小时）。
  这样既不会无限重试，也不会把站点永久钉死
- **请求去重**：同一 `站点/页号` 在排队或抓取期间，无论被请求多少次都只抓一次；
  同一站点同时最多只有一个补页任务在途（`syncReq` 标记保持到抓取真正结束）
- **每主机限流**：所有出站请求共用一个滑动窗口（默认 60 次/分钟，`-rate-limit`）。
  **语义是不阻塞**：配额不足立刻失败返回，不排队、不占 goroutine；
  被节流跳过的抓取只安排很短的重试（约 0.4s），且**不计入站点熔断**

### 展示顺序（不重复、不遗漏）

展示顺序的真源是**每站点一个去重的双向队列**，与「抓取记录」（`pages`）解耦：

| 操作 | 队列行为 |
|---|---|
| 刷新第 1 页 | 该页按上游顺序整体插入队首，旧条目自然顺移一格 |
| 抓更深的新页 | 新条目追加到队尾；中间页刷新只追加新出现的条目 |
| 解析详情 | 不动队列 |
| 下架/淘汰 | 从队列删除 |

因为是「移动 + 去重」而不是「整页覆盖」，上游在第 1 页插入新帖时：

- 新帖出现在最前 ✅
- 被挤到下一页的旧条目只是位置后移，**不会重复也不会消失** ✅
- 主键是 `站点:id`，位置变化**不会触发重新解析**（有测试保证）

`/api/scrape` 的两个新字段：

| 字段 | 含义 |
|---|---|
| `loading` | 后台正在补页，前端可稍后重试 |
| `has_more` | 还有站点没到最后一页，理论上能取到更多 |

## 接入新站点

抓取逻辑与站点耦合的部分全部在 `internal/provider/<站点>` 里，`store` 只认 `Provider` 接口：

```go
type Provider interface {
	Name() string
	MaxPages() int
	FetchList(page int) ([]Item, error)   // 列表页
	Enrich(it Item) Item                  // 详情 → 播放地址
	Refresh(it Item) (Item, bool)         // 只换直链签名（可选优化）
}
```

接入步骤：

1. 复制 `internal/provider/demo` 作为起点（约 150 行）
2. 改成新站的列表解析与详情解析
3. 在 `main.go` 的 `sites()` 里追加一行

接入后自动获得：多站分页、去重、直链缓存、失败重试、续播进度、线路二代理、站点过滤下拉。
唯一必须做到的是**最终交出一根 m3u8/mp4 地址**（`provider.IsMediaURL` 能识别）。

## 接口

| 接口 | 说明 |
|---|---|
| `GET /api/scrape?offset=0&limit=24` | 分页列表：`{offset,limit,total,count,items,pending,loading,has_more}`，可加 `&site=`/`&source=` 过滤 |
| `GET /api/map` | 完整 `id → 地址` 映射（含已下架条目） |
| `GET /api/pages` | 已缓存的上游页号（含 `by_site`） |
| `GET /api/status` | 映射总数、页数、待解析数、是否懒加载、各站点列表同步时间（`site_sync`） |
| `POST /api/resolve?id=<帖子号>&site=<站点>` | **按需解析**：只重解析这一条，返回 `{item,changed,waited}` |
| `GET /api/items` | 当前列表全部条目（受上限约束） |
| `GET /api/proxy?url=<目标地址>` | **线路二**：同源代理上游清单/分片/密钥 |

`/api/scrape` 的 `total` 是总条数，`pending` 是正在解析的数量。窗口跨页时会自动顺延抓取上游页，最多 6 页。旧参数 `?page=N` 仍可用（按每页 24 条换算）。

### 播放线路（线路一 / 线路二）

播放器顶部有一组线路开关，选择会记在 `localStorage`：

- **线路一（默认）**：浏览器直连原始视频地址，不占服务器带宽。
- **线路二**：`/api/proxy?url=...` 由服务端代取，解决跨域（CORS）、Referer 防盗链、运营商链路差异导致的播放失败。直连失败时会自动切到线路二重试一次，失败面板上也能手动互换线路。

线路二受启动参数控制：

```bash
./run.sh                 # 默认启用，页面显示“线路一 / 线路二”
./run.sh -proxy=false    # 关闭代理：不注册 /api/proxy，页面完全不显示线路开关
```

关闭时代码里也不会发起任何代理请求，之前存过“线路二”的浏览器会自动回落到直连。`GET /api/status` 的 `proxy` 字段告诉前端当前是否启用。

代理只对映射里出现过的播放主机（以及代理清单里发现的分片 CDN 主机）开放，并在拨号阶段校验目标 IP，内网/回环/链路本地/云元数据地址一律拒绝，避免成为公网开放代理或 SSRF 跳板。m3u8 会逐行重写（分片、`#EXT-X-KEY` 的 URI、`#EXT-X-MAP` 等）指向代理自身，否则相对路径分片会取错。


## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-addr` | `:8000` | 监听地址 |
| `-root` | `.` | 静态文件目录 |
| `-store` | `<root>/store.json` | 映射文件路径 |
| `-refresh` | `3h` | 上游列表同步间隔 |
| `-video-ttl` | — | **已废弃**（仅为兼容旧脚本保留，传了也忽略） |
| `-lazy` | `true` | 懒加载：只抓列表，直链等播放时按需解析。关掉则恢复「列表刷新即批量解析」 |
| `-keep` | `720h` | 下架映射保留时长（0 为永久） |
| `-workers` | `8` | 详情解析并发数 |
| `-max-items` | `10000` | 映射与接口的最大条数 |
| `-proxy` | `true` | 是否启用视频代理（线路二）；关闭后不注册 `/api/proxy`，页面也不显示线路二 |
| `-max-pages` | `30` | 单站点最多深挖到第几页，防止翻尾把上游抓一遍 |

## 支持的播放源

| 类型 | 处理方式 |
|---|---|
| 播放器接口页（`?id=…&sign=…`） | 调 `videos/playerurl` 换 m3u8 直链 |
| 第三方嵌入页（`/embed/<id>`，kt_player） | 抓 HTML，取 `flashvars.video_url` 得到 mp4 直链（会 302 到 CDN，支持 Range） |
| 两者都失败 | 保留网页播放页，前端用 iframe 打开 |

嵌入页的直链写在页面内联 JS 里，站点改版会让规则失效；失效时只是回落到 iframe，不影响其它条目。

## 懒加载（默认）

上游对我们是按 IP 限流的，列表一刷新就对几百条帖子逐个抓详情页，很容易整站 403。
所以默认策略是「只抓列表，直链等播放时再解析」：

```
列表线程（每 3 小时）            详情线程（-lazy=false 才会主动跑）
  └ 抓列表 → 入库 → 显示            └ 批量补直链
                                    ↓
用户点播放 ──→ 有直链？直接用
             └ 没有 / 播放失败 ──→ POST /api/resolve（只解析这一条）
                                     └ 换到新地址就原地重播
```

- **后台不主动抓详情**：新帖、翻页都只入库标题与链接，`play_url` 留空
- **播放时才解析**：列表没地址就直接解析；旧地址失效（`video.onerror`/HLS fatal）时
  也先请求一次重解析，拿到新地址就地重播，再不行才切线路、提示失败
- **同一条目只解析一次**：在途请求共享结果，1 分钟内重复请求直接复用（前端的
  重复点击不会放大对上游的请求）
- **顶栏显示各站点上次同步时间**：`/api/status` 的 `site_sync`，方便判断上游有没有更新

### 增量同步怎么判断「上游更新了」

每轮定时同步从第 1 页开始逐页往下比对，每抓一页就拿本页 id 和本地已有的 id 比：

| 本页情况 | 处理 |
|---|---|
| 出现本地已有的 id（例如上次排到 123，这次翻到含 123 的那页） | 说明已追平上次同步的位置，**立即停止**，后面的页不再抓 |
| 整页都是没见过的 id | 还没追平，继续翻下一页 |
| 一直撞不到（如首次同步） | 最多翻 `maxIncrementalPages = 5` 页就收手，避免触发风控 |

顺序处理：第 1 页按上游顺序整体插到队首（旧条目自然后移一格），更深页只把
「新增的」接在第 1 页之后。所以效果就是——**上游插到第 1 页的新帖出现在最前，
被挤下去的旧帖只是位置后移，不重复也不遗漏**。已缓存的深层页不会被反复抓。

要恢复旧行为（列表刷新就批量解析）用 `-lazy=false`。

## 并发与去重

所有会打到上游的路径都有锁，不会重复请求：

- **列表页**：`listMu` 全局串行 + 至少 150ms 间隔；每页另有 `pageLock`，同一页不会被并发抓取
- **窗口补页**：`windowMu` 串行，先到的把页抓好，后到的直接命中缓存
- **单条详情**：`pending`（已入队）+ `inflight`（解析中）双重去重；已有直链的条目后台不会再碰
- **按需解析**：同一条目在途只发一次请求，后来者等同一份结果；1 分钟内重复请求复用上一次结果
- **失效保护**：上游返回空列表、单页超过 1000 条、或条数骤减到 1/3 以下时，判定异常并沿用缓存

## 前端

- 顶部显示总条数；底部显示页码按钮（首尾页 + 当前页两侧，其余省略）与跳转输入框

## 数据备份

`store.json` 是唯一数据源，建议定期备份。仓库里的 `backups/` 存放了最早的 Python 版本与 `data.json`，仅供对照，服务不再读取。
